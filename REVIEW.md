# Prioritized product and code review

Scope: current Python/pygame source, existing rendered title/field/lesson/shop/result/graph screens, 25 tests, and targeted deterministic reproductions. The suite passes outside the Windows sandbox; the sandbox alone blocks the temporary rename in the save test. Tests prove numerical and basic gameplay correctness, not learning effectiveness. No learner study or frame-time benchmark was performed.

Assumption: “simple geometry 3D” means an actual solid-geometry battlefield, including the tower, tanks and road, with a fixed elevated camera. The targeting curriculum can initially remain on a flat ground plane. Recommendations below are a backlog, not changes already implemented.

Priorities: **P0** blocks credible guided teaching or permits broken progression; **P1** belongs in the next playable version; **P2** improves reliability, access, polish or extensibility. Within each theme, items are ordered by impact. Effort estimates are relative: S = localized, M = several components, L = architectural work.

## 1. Colour, clarity and visual identity

**V1 — P1 / M: Replace the near-monochrome visual system.** `ui.py:7–16`, `panel():69`, `draw_field():282`. Background `(12,19,29)`, panel `(22,33,46)` and battlefield `(17,29,38)` are too close in brightness. The grey road occupies a large area and most accents are thin teal lines. Use a deep-indigo application frame `#18213B`, elevated cards `#263658`, pale task cards `#F2F6FF` with ink `#14213D`, green terrain `#4A986B`, sand road `#D8B889`, violet primary actions `#6D28D9`, and white primary button text. Retain cyan `#22D3EE` for prediction, amber `#FBBF24` for projectiles, coral `#FB7185` for error/damage. Treat these as proposed tokens and validate contrast in the final combinations. Keep tank-class colours distinct from controller and status colours through labels and shapes.

**V2 — P1 / M: Make the current task the strongest interface element.** `draw_bottom():384` dedicates 242 pixels to general field notes; the inspector is another 464-pixel-wide card of similar weight. Give the battlefield about 70% of available width and use a 320–380-pixel coaching rail. Put “Your task: predict where this tank will be in 1 s” above one primary “Run experiment” button. Collapse full pseudocode and advanced telemetry until relevant. The bottom strip should show simulation controls and compact progress, not a second wall of instructions.

**V3 — P1 / S: Strengthen typography and actual-size legibility.** `Interface.__init__():26`, `button():82`, `draw_controller():437`. Current screens look thin and uniformly weighted. Use a dependable regular body face, bold 24–28px task titles, 20–22px body copy and 17–18px minimum secondary text at logical resolution. Use monospace only for values and executable expressions. At the permitted 960×640 window, 14px logical text is only about 9.3 screen pixels: a responsive layout/text-size setting is needed, not just bigger logical fonts. Bundle a redistributable font with its licence for consistent rendering.

**V4 — P1 / S: Give buttons distinct semantic states.** `button():74`, `slider():86`. Today selected, primary and enabled controls mostly differ by an outline; there is no pressed or keyboard-focus state. Use a solid violet primary button, cyan selected pill with a check, neutral secondary controls, and a distinct focus ring. A locked algorithm needs a lock symbol and “Opens in lesson 3,” rather than an unexplained disabled button. Separate disabled, insufficient funds, installed, selected and completed states. Use a labelled warning state for actuator saturation.

**V5 — P1 / M: Make actions and outcomes feel consequential.** `draw_field():327` currently supplies expanding hit/leak rings; `notify():74` supplies a generic five-second toast. Add a 70–100ms muzzle flash, 100–140ms barrel recoil, short shell trails, 150–250ms impact sparks, 500–700ms credit popups and a 200ms step-complete check animation. Failed shots should briefly retain their aim cross and nearest tank position. Colour a result according to outcome, not every toast teal. Add restrained optional firing/hit/completion sounds, volume/mute and reduced-motion settings. These effects must follow simulation events, never determine timing.

**V6 — P1 / S: Improve spacing and iconography.** `draw_bottom():391`, `draw_controller():437`, `draw_shop():474`. Use an 8px spacing scale, 24px panel padding and at least 44px rendered control targets where possible. Reset gains and Error graph are currently only 22 logical pixels high. Add small geometric icons with labels: play triangle, pause bars, sensor prism, shop bag/hexagon, curved reset arrow, lock, tick. Group transport, learning and debugging controls rather than giving all seven bottom-row buttons equal visual weight.

**V7 — P1 / S: Separate visual channels.** Gold currently means shell, gold tank, brake zone, money and formula; teal means prediction, selection, success and primary action. Keep prediction as a cyan cross plus dashed line; use a white solid barrel-direction ray, amber projectile trail, striped brake zone, and a distinct velocity arrowhead. Show tank classes with B/R/G plus different roof symbols. Preserve these identifiers in 3D.

**V8 — P2 / S: Make the title and shop preview the actual game.** `draw_title():219`, `draw_shop():474`. The title is mostly empty dark space and the shop is six text rows. Show the low-poly tower and a looping interception on the title. Show upgrade icons, current → next numeric effects, visible installed parts and an explicit “No next level” state. For the sensor, include a preview observation showing `colour: unavailable → red`, and highlight the new code branch.

## 2. Guided learning that checks evidence

**L1 — P0 / L: Replace page progression with a lesson runner.** `Lesson` in `lessons.py:5` currently holds text, wave parameters and an algorithm unlock. `lesson_next()` in `ui.py:118` only increments a page, and Escape closes the explanation. `game.py:274` checks final hit counts, accuracy and two final settings. Add `LessonStep`, `LessonProgress`, `LessonRunner` and typed simulation/input events, outside rendering. Each step needs: task, enabled actions, setup, required evidence, completion rule, hint ladder, misconception feedback, reward and next-step id. Model the flow as brief → predict → act → observe → explain → congratulations → next task. A page read or slider click is not evidence of mastery.

**L2 — P0 / M: Track actions and trial results, not final settings.** Emit events for strategy changes, parameter changes, purchases, sensor observations, branch execution, shot launch/resolution and submitted predictions. Track which strategy/gains produced each shot. Otherwise a learner can switch to the required algorithm immediately before wave completion. A tuning step should require a completed measurement window under the changed setting, then a comparison or application task. Relevant current sites: `set_algorithm():159`, `buy():166`, `tick():206` in `game.py`; slider setters in `ui.py:428` currently mutate controller fields directly.

**L3 — P0 / M: Rewrite the eight lessons as short validated experiments.** Preserve the overall sequence, but require the following evidence:

1. **Direct aim:** ask “Will the shell hit?”; run a crossing shot and resolve the miss; ask the learner to place a future-position marker; then land three predictive practice shots. Baseline misses must not reduce the assessed accuracy.
2. **Flight time:** supply a concrete distance and speed; ask for time, then lead distance. Use a changed distance or faster shell as a transfer question. Detect the submitted values within a declared tolerance.
3. **Intercept:** assemble/select `p + v*t`, choose the earliest positive root, and verify equal arrival times on two different target speeds. Reveal the quadratic after the simpler time/distance experiment.
4. **Acceleration:** run the same boosting target with CV and acceleration prediction. Require measuring and explaining the difference. Current deterministic lesson 4 gives **9 hits / 12 shots for both Intercept and Adaptive**, so it does not currently demonstrate the benefit of acceleration; design a scenario where the models differ measurably before setting a mastery threshold.
5. **Colour sensor:** purchase it, compare the same trial OFF and ON, observe actual red/gold branches, then classify an unseen tank. Merely owning the upgrade is insufficient.
6. **P:** collect a low-gain tracking baseline, change P, then compare error and overshoot over a defined interval. Reward a stable improvement, not one exact gain value.
7. **I, then D:** split this into two steps. First hold a fixed direction under bias and demonstrate I reducing persistent error. Then use a step change and demonstrate D reducing overshoot. Keep P and motor configuration constant during each comparison.
8. **F:** compare a moving aim reference with F=0 and F enabled while keeping P/I/D constant. Validate reduced tracking lag, then complete a mixed transfer wave without coaching.

Proposed initial tolerances such as a 20% error reduction or a 3-degree tracking band need balancing against the new controlled scenarios; they are not measured properties of the current waves.

**L4 — P0 / M: Require evidence for each PIDF concept.** Reproduced: with Colour aware and gains **P=8, I=D=F=0**, lessons 6, 7 and 8 all pass, scoring 8/21, 10/23 and 16/25 hits respectively. `game.py:106` also auto-installs I/D and F on later stages. Start a new term at zero for its experiment, keep other variables fixed, and measure its actual effect. Separate “you survived the wave” from “you demonstrated integral action.”

**L5 — P1 / M: Give precise, supportive feedback.** `finish_wave():281` currently uses generic report hints. Add persistent in-context feedback: “You changed the lead, but have not run the trial yet”; “The shell arrived 0.3s after the tank crossed your marker”; “P helped the response, but peak overshoot increased”; “Sensor purchased; now observe a RED branch.” After repeated difficulty, offer a highlighted control, then a worked example, then a retry on a slightly changed scenario. Preserve completed steps when retrying one failed experiment. Allow explicitly labelled free-play/skip-for-now, but do not award mastery for a skipped step.

**L6 — P1 / M: Add the requested congratulations screen after verified milestones.** `draw_result():496` only reports wave statistics, and `draw_victory():515` appears after the entire campaign. Add a dedicated step/lesson success state: a bright badge, “Congratulations — you predicted the intercept,” the actual before/after measurements, the learner's completed expression or active branch, a short “why this worked” sentence, and the unlocked tool. Use actual session data rather than canned numbers. Offer “Replay my solution” and one primary “Continue.” Pause advancement until the learner chooses Continue. Reduced motion should retain the same content without particles or screen movement.

**L7 — P1 / M: Persist learning progress separately from currency.** `persistence.py:31` currently stores only stage, currency, upgrades and won. Add a save schema version, lesson/step ids, completed evidence, best trial metrics, strategy, lead, gains and accessibility settings. Award each mastery reward once using a stable reward id. Save after completing an assessed step and after confirming its congratulations screen. Resume at the next incomplete step; migrating an old save must not erase it or assume all earlier skills were demonstrated.

**L8 — P1 / M: Add algorithmic thinking tasks.** `draw_inspector():368` shows static pseudocode, not an editable reasoning task, and a branch label below it. Highlight the executing line/branch; show substituted numeric inputs and intermediate values; add reorderable expression blocks, choose-the-condition questions, and a prediction before running the simulation. Offer “What will change if shell speed doubles?” before revealing the outcome. Ordinary Python files can remain the advanced editing route; an unrestricted in-game Python execution box is unnecessary.

## 3. The requested simple geometric 3D game

**D1 — P1 / L: Change the renderer before polishing the current sprites further.** `ui.py:269` creates rotated 2D tank Surfaces, and `draw_field():330` draws the tower as circles and a line. Introduce `renderer3d.py`, `camera.py`, `geometry.py` and a HUD/presentation boundary. Preserve the pure-Python targeting/controller core. Keep world coordinates separate from screen coordinates: initial physics can use planar `(x,z)` values, with a fixed visual height for tanks and the barrel.

**D2 — P1 / M: Use simple solids and a stable camera.** Make the tower a 12-sided cylinder base, cuboid turret and cylinder/cuboid barrel; tanks can be two track boxes, a coloured chassis and a small turret. Add an extruded road, flat green terrain, a geometric base and simple contact-shadow discs. Start with a fixed orthographic camera at about 50–55 degrees elevation and 45 degrees azimuth. Lock it during early lessons, then optionally allow zoom/orbit and always provide Reset camera. Avoid tall scenery that hides lead markers or tanks. An orthographic projection still renders real 3D solids and supports clear comparisons.

**D3 — P1 / M: Retain pygame for input/windowing, add a real 3D renderer.** Proposed implementation: pygame OpenGL display plus ModernGL. Additional direct dependency: `moderngl`, with a tested version pinned when implementing. Pygame supports an OpenGL display and ModernGL can adopt an active window context. The current final `window.blit()` path in `ui.py:216` cannot simply be kept on an OpenGL display: draw the HUD to a transparent Surface and composite it as a texture, or use a GPU UI renderer. Handle GL resource lifecycle during resize/fullscreen/context recreation. The current SDL dummy UI tests do not prove GL support; preserve simulation tests and add separate renderer tests and real GPU smoke checks.

Sources: [pygame display](https://www.pygame.org/docs/ref/display.html), [ModernGL context creation](https://moderngl.readthedocs.io/en/stable/the_guide/getting_started/low_start/creating_context.html).

**D4 — P1 / M: Make 3D serve the teaching.** Project a labelled intercept ring on the road, draw a ghost tank at the predicted location, show velocity and desired/actual turret rays, and keep annotations legible above geometry. Render an angular error arc at the turret and a shot-resolution ghost at the miss location. Use consistent physics and display launch origins; `Tower.fire():106` currently launches mathematically from the pivot while the visual barrel extends 46px. Test screen/world transforms and picking. Vertical ballistics and gravity should be a separate optional lesson once planar interception is understood.

## 4. Confirmed bugs and misleading behaviour

**B1 — P0 / S: Fix stale shop return state that can skip lesson 5.** `ui.py:124,163,488` keeps `shop_return` on Interface, but `game.py:117` enters the shop directly. Reproduction: open Workshop from the lesson-4 result; return, advance to lesson 5, launch without a sensor, purchase it, and return. The retained return target is `result`, and the previous `success=True` was not cleared by `reset_world()`. Continue advances to lesson 6 with zero lesson-5 hits. Use a single `open_shop(return_to)` transition, clear result state when preparing a new stage, and guard `advance()` with a fresh completed-lesson record. Add this exact navigation regression test.

**B2 — P1 / S: Preserve the learner's tuned gains.** `reset_world():62` constructs a new Tower; `prepare_stage():105–110` then replaces gains with presets. Reproduced: `(8,1,0.3,0)` becomes `(4,0.65,0.22,1)` on advancement. Preserve known gains, deliberately introduce only the new experimental term, and save/restore the selected algorithm and lead as well. Show any intentional preset change before applying it.

**B3 — P1 / S: Correct the apparent firing range.** `ui.py:305` draws radius **190**, but `game.py:221` targets within **530**. Either draw the true range clipped to the battlefield, label the current circle as an illustrative reference, or remove it. A teaching overlay must not visually contradict the simulated rule.

**B4 — P1 / S: Permit shots at stationary detected tanks.** `game.py:237` requires estimated velocity above 1. Reproduced: a stationary detected tank receives **zero shots in three seconds**, despite valid intercept math. Track sensor confidence/sample count separately from speed, then fire at valid stationary targets. This also blocks the proposed fixed-target integral exercise until corrected.

**B5 — P1 / M: Keep motor dynamics consistent without a valid target.** `game.py:223–233` does not update the turret when a selected target has no intercept; without a target it resets the controller and omits the configured bias. Separate motor integration from target availability, maintain a defined hold/idle command, and apply the disturbance consistently. Avoid silently erasing integral memory unless the exercise or reset action requires it.

**B6 — P1 / M: Track shot outcomes instead of treating every launched shell as a resolved trial.** `game.py:250` accepts a hit on any tank; `:274` ends the wave as soon as tanks are gone even if shells remain. The generic accuracy denominator includes pending or redundant launches and cannot identify prediction vs motor error. Record intended target, launch time/aim, expected flight, actual resolution and miss distance. Assess resolved shots in the relevant trial; allow a bounded resolution phase before reporting. If several collisions happen in one tick, choose earliest swept impact rather than the first tank in the list.

**B7 — P1 / M: Make save/reward transitions transactional.** `finish_wave():285` adds credits but saves only later on a shop purchase or advancement. Purchasing from a success screen can save the reward against the still-current stage, while quitting immediately after success can lose it. Save a completed-wave/result state and a once-only reward marker atomically, together with the next progression decision. Do not permit repeated completion calls to duplicate rewards.

**B8 — P2 / S: Distinguish a search limit from mathematical impossibility.** `targeting.py:91` searches four seconds, but `ui.py:377` says “No feasible intercept.” Display “No intercept found within 4s” for bounded search failure. Also show which model assumes straight-line motion and which follows path corners; otherwise a corner miss looks like incorrect algebra.

**B9 — P2 / M: Handle target reacquisition and selection intentionally.** `TargetSelector.choose():225` retains an in-range target even if it has no feasible interception. Select a feasible alternative when appropriate. Reset or suppress desired-rate feedforward on target-id changes: `control.py:40` currently interprets reference jumps as a large, clipped desired velocity. Separate acquisition transient metrics from steady tracking metrics.

## 5. Usability, accessibility and pacing

**U1 — P1 / M: Make plots live beside the controls.** `show_graph():451` changes mode so `Game.update()` stops. The modal also removes slider access. Add compact live error/desired/actual traces next to the current term control, plus a separate freeze/inspect recorder. Allow a fixed scale for matched baseline comparisons; the shared autoscale in `plot():562` can squash the other terms after a large P spike.

**U2 — P1 / M: Add keyboard focus and numeric gain entry.** `events():128` supports shortcuts, but buttons and sliders have no Tab navigation or selected-control arrow adjustment. Add Tab/Shift-Tab, Enter/Space activation, arrow-key adjustments, numeric fields and visible focus. Support common shortcuts consistently across modal screens. Display structured instructions in an accessible companion lesson document; pygame does not provide a screen-reader interface merely by drawing text.

**U3 — P1 / M: Replace uniform canvas shrinking with responsive layout.** `Interface.WIDTH/HEIGHT`, `transform():39` and hardcoded rectangles assume 1440×960. Add a compact arrangement, text-size option and scrollable coach panel. Verify 1280×720, 1366×768, high-DPI displays and larger fonts. Do not force-resize a small window in a way that exceeds the available desktop.

**U4 — P1 / S: Keep notifications away from controls.** `draw():210` places a toast at y=901–943, covering the lower part of the transport buttons and the controller's reset/graph row. Reserve a notification region above controls; errors should remain available until understood. Add persistent task-specific hints rather than five-second-only guidance.

**U5 — P1 / M: Separate learning assessment from campaign economy.** Upgrades can change shell speed, motor dynamics or damage while a lesson is trying to compare algorithms. Use fixed equipment for assessed demonstrations and enable the shop for subsequent transfer waves. Guarantee the required sensor with a clearly explained grant, not an unexplained balance correction in `prepare_stage():102`. Explain that the base is rebuilt between lessons, since `reset_world():68` restores it to 16 every time.

**U6 — P2 / S: Explain the shot reservation policy and actual wait reason.** `game.py:235` holds fire while a shot is due to arrive, even with reload complete. This can make reload upgrades appear ineffective and the player cannot tell whether the turret is waiting for reload, sensing or an existing shell. Show a wait-reason label and allow appropriate multi-target scheduling later; use the real policy in the shop's upgrade-effect preview.

**U7 — P2 / M: Add a lesson map, replay and notebook before full campaign completion.** Lesson selection currently appears only on `draw_victory():519`. Show completed, in-progress and locked skills; let the learner replay completed experiments without overwriting campaign currency. Keep discovered formulas and personal baseline/after results in a notebook. Offer assisted practice independently of mastery records.

**U8 — P2 / S: Add safety for ordinary navigation.** New campaign overwrites progress immediately via `draw_title():229`. Add a confirmation with save-slot selection or backup. Auto-pause on focus loss/minimize. Provide clear menu/help access from Ready and result screens, not only while a wave is paused. Retain window size and accessibility settings.

## 6. Code structure, performance, tests and delivery

**C1 — P1 / M: Use explicit scene and lesson state.** Replace string state mutation across Game and Interface, `getattr` fallbacks and UI-owned return destinations with a typed scene enum/router and transition methods. Separate campaign profile, wave state, lesson progress and presentation settings. This directly prevents B1. Keep the existing pure targeting/control boundary.

**C2 — P1 / M: Store diagnostic events as domain data.** Add `ShotRecord`, `TrialMetrics` and `LessonEvent` records. Derive overlays, coach feedback, replay and assessment from these records. Rendering should read snapshots, not be the only place that knows a gain changed. Define an explicit targeting Strategy protocol and typed parameters/results so adding algorithms does not depend on magic list indices.

**C3 — P2 / M: Remove duplicated behaviour and prediction rules.** Red/gold constants live in `Tank.update():46`, `ColourAwareStrategy.aim():170`, `ColourAwareStrategy.forecast():201` and lesson strings. The latter two predictors even integrate with different timesteps. Use one published behaviour profile/rule implementation shared by the world and predictor, but keep the predictor limited to its permitted observations. Derive explanations from those profiles. Put wave goals and completion criteria on Lesson instead of parallel tuples and hardcoded stage comparisons.

**C4 — P2 / M: Cache predictable rendering and forecast work after profiling.** `tank_shape():270` allocates/rotates Surfaces for every tank every frame, `text():46` re-renders labels, `draw_field():286` redraws the grid, and `draw():214` rescales the entire frame. Cache static layers, fonts/text, and reusable geometry. `ColourAwareStrategy.aim()` rebuilds a trajectory on each 120Hz physics tick despite sensors sampling much slower. Cache a forecast by observation/model version and advance/interpolate its reference safely. Collect simulation/render frame times before choosing a lower solver rate; preserve accurate launch-time aiming. For 3D, create meshes and buffers once and batch compatible draws.

**C5 — P1 / M: Test learning failures and real navigation, not just winnability.** `tests/test_core.py:162` selects strategies and P=8 automatically; `tests/test_ui.py:26` mostly verifies that screens render without throwing. Add regressions for stale shop returns, no-evidence advancement, P-only PIDF completion, skipped steps, persisted mastery, reward duplication, gain retention, stationary targets, pending shots and sensor-off assessment. Test the entire campaign as a sequence, not only independently reset waves.

**C6 — P2 / M: Add visual and performance verification.** Check text bounds, control visibility, focus order and minimum rendered font sizes. Save deterministic screenshots with image-difference tolerance rather than expecting identical platform font rasterization. For 3D add camera projection/picking, depth ordering, overlay visibility, resize/fullscreen resource lifecycle and GPU smoke tests. Keep pure numerical tests runnable without a display. The current numerical tests passing should not be described as evidence that users learned the content.

**C7 — P2 / M: Improve installation and save resilience.** `play.bat` works after a Python environment is installed but does not package the game. Add a packaged Windows build and a clean-machine launch check. Move user saves/settings to a user-data directory for packaged installs, preserve a backup and schema migrations, and distinguish missing, corrupt and unwritable saves rather than treating all as a fresh profile in `load_progress():27`. Add a clear recover/export/reset path. Keep dependency pins and licence notices with the release.

## Suggested implementation order

1. Fix the lesson-skipping shop transition and gain loss. Add regression tests.
2. Implement the lesson runner, event records and one complete observe → predict → act → evidence → congratulations loop.
3. Build the geometric 3D battlefield and colourful task-first HUD around that first lesson.
4. Validate the first lesson with someone new to the game; check that they can explain the intercept and solve a changed example.
5. Convert the remaining lessons, splitting I/D and requiring a separate F comparison. Balance scenarios by measured model/controller differences.
6. Add resumeable mastery records, accessible controls, replay/notebook, audio/motion settings and packaging.
7. Profile and optimize the completed 3D renderer and predictor workload, then run navigation, visual and hardware smoke checks.
